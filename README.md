# mebody

**내 몸의 코드를 찾는 웰니스 셀프 체크**

32개 질문에 답하면 네 축으로 내 몸의 경향을 읽고,
16가지 **mebody Code** 중 내 코드와 오늘 할 관리 루틴을 받습니다.

## mebody 가 하는 일

몸이 불편한데 어디가 문제인지 모르겠고, 운동을 시작해도 뭘 해야 할지 모르겠다 —
그 지점에서 시작합니다.

### 1. 32문항으로 내 몸을 읽습니다

목·어깨·골반·유연성 **네 축**을 각각 묻습니다.
"귀가 어깨보다 앞으로 나와 있다", "10초 유지하기 어렵다" 처럼
**거울 앞에서 바로 확인할 수 있는 것**만 묻습니다. 자가 측정으로 답할 수 없는 질문은 넣지 않습니다.

### 2. 16가지 코드 중 내 코드가 나옵니다

네 축의 조합으로 `FRRS`(앞서가는 잠금 로봇) 같은 코드가 나옵니다.
캐릭터와 한 줄 설명이 붙어서, **기억하고 남에게 말할 수 있는 형태**가 됩니다.

결과 화면은 축마다 "**내 답변 기준**" 근거를 함께 보여줍니다 —
어느 문항에 어떻게 답해서 이 결과가 나왔는지 그 자리에서 확인할 수 있습니다.

### 3. 오늘 할 것 하나를 줍니다

코드가 나왔다고 끝이 아닙니다. 그날 할 **공통 스트레칭**과
축 우선순위에 맞춘 동작이 매일 나옵니다. 14일 루틴으로 이어집니다.

한 달에 20일을 채우면 보너스가 쌓입니다. 적립금은 마켓에서 관리 도구를 살 때 씁니다.

### 4. 몸 기록을 남깁니다 — 마이 바디 노트

하루에 한 번, 네 가지만 고르면 끝납니다.
**불편했던 곳 · 더 편했던 쪽 · 그날 많이 한 활동 · 컨디션.**

쌓이면 보입니다 — *"최근 30일 · 어깨 8번"*.
해석하지 않고 반복만 보여줍니다. 판단은 사용자 몫입니다.

### 5. 전문가와 함께 볼 수 있습니다 — VIP CARE

트레이너·물리치료사가 보낸 **초대 링크를 열고 직접 동의**해야만 연결됩니다.
연결되면 전문가가 내 결과와 몸 기록을 보고 동작을 추가하거나 한마디를 남깁니다.

전문가는 **읽기만** 합니다. 사용자의 기록을 고치는 경로 자체가 없습니다.
동의를 거두면 **그 순간부터** 전문가 화면에서 사라집니다.

## 우리가 지키는 것

mebody 는 건강을 다룹니다. 그래서 기능보다 먼저 정한 원칙이 있습니다.

### 진단하지 않습니다

의료 행위가 아닙니다. 화면 어디에도 "진단·치료·교정·처방" 이라고 쓰지 않습니다.
몸 기록의 색도 **경고색(빨강)을 쓰지 않습니다** — 색이 판정으로 읽히면 안 되기 때문입니다.
컬럼 이름에 `pain`·`symptom`·`diagnos` 가 들어가지 않는지 자동 검사가 막습니다.

### 화면은 시스템이 보장할 수 있는 것만 말합니다

- 확률이나 금액을 미리 약속하지 않습니다
- 0원일 때 "0원 적립" 이라고 쓰지 않습니다 — 처음 쓰는 사람에게 첫인상이 "아무것도 못 받는 곳" 이 됩니다
- 연결이 끊기면 **끊겼다고 말합니다**. 빈 화면을 보여주고 사용자가 고장으로 오해하게 두지 않습니다
- 사업자 정보·평점·후기를 **지어내지 않습니다**. 없으면 비워 둡니다

### 남의 기록은 보이지 않습니다

모든 테이블에 행 단위 보안(RLS)이 걸려 있습니다. 회원끼리도, 전문가도 예외가 없습니다.
권한 판단은 화면이 아니라 **데이터베이스 안에서** 합니다 — 화면만 믿으면 API 를 직접 부르는 쪽으로 뚫립니다.

공유 링크에는 **결과 id 를 싣지 않습니다.** 16가지 공개 분류인 코드만 담깁니다.

### 한 곳에서만 정합니다

같은 값을 두 군데 적으면 **반드시 어긋납니다.** 그래서 전부 출처를 하나로 둡니다.

| 값 | 단 하나의 출처 |
|---|---|
| 앱 버전 | `package.json` → 안드로이드 versionCode 자동 계산 |
| 캐릭터 이름 | `bodyCodeCalculator.ts` → 공유 페이지가 읽어감 |
| 검색 노출 문자열 | `build-seo.js` → sitemap·canonical·OG·JSON-LD·FAQ |
| 법적 문구 | 앱과 웹 문서가 갈라지면 검사가 막습니다 |

## 어떻게 만들었나

### 구성

```
                   ┌──────────────┐
   홈페이지·관리자   │ Spring Boot  │  계정 · 주문 · 전문가 API
   전문가 콘솔      │   (Railway)  │
                   └──────┬───────┘
                          │
   Android APK  ┌─────────┴────────┐   React 18 + TypeScript + Vite
   웹 (Vercel)  │   mebody 앱      │   Capacitor
                └─────────┬────────┘
                          │
                   ┌──────┴───────┐
                   │   Supabase   │  Auth · Postgres(RLS) · Storage
                   └──────────────┘
```

한 벌의 코드가 **웹과 안드로이드 앱 둘 다**로 나갑니다.

### 스택

| | |
|---|---|
| 앱 | React 18 · TypeScript · Vite 6 · Capacitor (Android) |
| 서버 | Spring Boot · JPA |
| 데이터 | Supabase — Auth, Postgres, Storage, RLS, SECURITY DEFINER 함수 |
| 광고 | AdMob 배너 · 보상형(서버 검증 SSV) |
| 배포 | Vercel (웹) · Railway (서버) · Google Play (앱) |

### 품질

숫자로 관리합니다.

| | |
|---|---|
| 검증 스위트 | **44개** |
| 개별 검증 항목 | **1,000개 이상** |
| 소스 | 120개 파일 · 약 27,000줄 |
| 마이그레이션 | 52개 (적용 상태를 스위트가 판정) |

검증은 "통과하면 좋은 것" 이 아니라 **배포를 막는 관문**입니다.
빌드 명령 안에 들어 있어서, 통과하지 못하면 APK 가 만들어지지 않습니다.

스위트는 기능별로 나뉘어 있습니다 — 적립금 상한, 전문가 권한 경계, 공유 링크에 개인정보가
섞이지 않는지, 탈퇴 시 지워지는 것과 남는 것, 광고 문구가 정책을 어기지 않는지, 앱이 서버에
실제로 닿는지.

> 한 가지만 예로 들면: 앱이 부르는 서버 주소를 **소스에서 뽑아** 실제 앱의 출처로
> 요청을 보내 보는 검사가 있습니다. 브라우저에서만 테스트하면 절대 안 보이는,
> **앱 안에서만 막히는** 문제를 잡기 위해서입니다.
