# jjh 앱·서버 통합 검증 보고서

검증일: 2026-09-16  
대상: 로컬 앱 `mebody-jjh`, 로컬 Spring 서버 `mebody-server`, 현재 연결된 Supabase 검증 환경  
원칙: 앱·서버 소스 수정 없음, 실결제 없음, 생성된 가입 검증 계정은 검사 종료 시 삭제

## 1. 판정

앱의 일반 이동과 뒤로가기는 이전 보고서 이후 크게 개선됐습니다. 이번 실행에서는 설문 10번에서 로그인 화면을 열었다가 취소해도 10번과 기존 답변이 유지됐고, 새로고침 후에도 같은 문항이 복원됐습니다. 하단 탭을 `미션 → 루틴 → 마켓 → 내 상태`로 이동한 뒤 브라우저 뒤로가기를 누르면 `마켓 → 루틴 → 미션 → 이전 결과 화면`으로 정확히 복귀했습니다.

그러나 현재 상태를 운영 준비 완료로 판정할 수는 없습니다. 개인정보·약관과 가입 동의 증적, 계정 보안, 안전 문항, 마이페이지 오류 표시에서 높은 우선순위 문제가 확인됐습니다.

가장 먼저 처리할 항목은 다음과 같습니다.

1. 앱과 서버의 개인정보처리방침·이용약관이 모두 최종 문서가 아닌 **플레이스홀더**입니다.
2. 가입 화면에서 필수 체크를 받아도 서버에는 동의한 문서의 종류·버전·시각·문구가 저장되지 않습니다.
3. 앱 가입과 서버 웹 가입의 필수 동의 문구가 다릅니다. 서버 웹 가입에는 “의료 진단이 아님” 확인이 없습니다.
4. 서버는 비밀번호 최소 길이를 1자로 안내하지만 실제 Supabase는 8자를 요구해 가입이 실패합니다.
5. 이메일·휴대폰 소유 확인이 모두 꺼져 있습니다. 특히 휴대폰은 실제 SMS 인증이 아니라 별칭 이메일로 처리됩니다.
6. 동작 검사 문항은 “통증·어지럼 시 중단”을 안내하지만 중단 사실을 선택·저장할 버튼이 없습니다.
7. 마이페이지에는 회원 탈퇴가 없고, 조회 장애가 “기록 없음·무료 회원”처럼 보일 수 있습니다.

이 문서는 기능·표시·데이터 흐름을 확인한 기술 검증 보고서입니다. 최종 법적 문구와 동의 범위는 실제 사업 구조, 위탁사, 결제 방식, 광고 SDK를 기준으로 별도 법무 검토가 필요합니다.

## 2. 검증 범위와 방법

- 앱은 운영 DB 쓰기를 막은 별도 로컬 Vite 주소에서 비회원 플로우와 브라우저 이력을 실행했습니다.
- 서버의 `/`, `/privacy`, `/terms`, `/health`, 공개 인증 설정은 실행 중인 로컬 서버에서 읽었습니다.
- 앱·서버의 가입 요청 DTO, 동의 UI, 법적 문서, 광고, 결제, 프로필, 주문, 멤버십, 측정 기록 코드를 교차 검토했습니다.
- 가입 API 검증 스크립트는 테스트 계정을 만들고 로그인 동작을 확인한 뒤 생성 계정을 모두 삭제했습니다.
- DB 검증 스크립트는 `BEGIN` 안에서 실행되고 마지막에 `ROLLBACK`되는 항목만 사용했습니다.
- 실결제, 주문 생성, 구독 활성화, 실제 이메일·SMS 발송, 실제 Android 기기 AdMob 표시는 실행하지 않았습니다.

## 3. 높은 우선순위 문제

### A01 · 치명적 · 공개 중인 개인정보처리방침과 이용약관이 플레이스홀더

- 구분: 브라우저 실행 + 코드 확인
- 화면: 앱 `/privacy.html`, `/terms.html`; 서버 `/privacy`, `/terms`
- 실제: 네 URL 모두 HTTP 200으로 열리지만 본문에 “본 문서는 플레이스홀더입니다”, “실제 기준으로 교체하세요”, “법무 검토 후 반영”이 그대로 노출됩니다.
- 기대: 시행일, 개정 이력, 실제 수집 항목, 목적, 보유 기간, 위탁·국외 이전, 권리 행사 방법, 담당자, 유료 정책이 확정된 문서가 노출돼야 합니다.
- 사용자 영향: 사용자는 어떤 데이터가 누구에게 어떤 기간 동안 처리되는지 알 수 없고, 체크한 동의의 대상 문서도 확정되지 않습니다.
- 코드 위치: `public/privacy.html`, `public/terms.html`, 서버 `src/main/resources/static/privacy.html`, `terms.html`
- 개선: 한 개의 승인된 원문과 버전을 기준으로 앱·서버 페이지를 생성하고, 문서 ID·버전·시행일을 표시합니다.

### A02 · 치명적 · 필수 동의가 서버에 증적으로 저장되지 않음

- 구분: 요청 구조·DB 코드 확인
- 진입: 앱 회원가입 또는 서버 웹 회원가입에서 필수 체크 후 제출
- 실제: 앱은 서버에 `identifier`, `password`, `displayName`만 보냅니다. 서버 `PublicSignupRequest`도 동일한 네 필드만 받습니다. 동의 종류, 약관 버전, 동의 시각, 수집 경로, 철회 상태를 저장하는 처리와 테이블이 없습니다.
- 기대: 서버가 필수 동의를 다시 검증하고 `user_id`, `document_type`, `document_version`, `agreed_at`, `channel`, `text_hash` 등 변경 불가능한 증적을 남겨야 합니다.
- 사용자 영향: 체크박스는 보이지만 어떤 문서에 언제 동의했는지 서버에서 입증하거나 버전 변경 후 재동의를 판단할 수 없습니다. API를 직접 호출하면 UI 체크 없이도 가입 요청이 가능합니다.
- 근거: 앱 `src/api/signup.ts:39-55`, 서버 `PublicSignupRequest.java:11-17`, `PublicAuthService.java:85-105`
- 개선: 가입 API DTO에 명시적 동의 항목과 문서 버전을 추가하고 서버에서 필수값·현재 버전을 검증한 뒤 별도 동의 이력에 저장합니다. 진단 동의도 결과 또는 세션에 안전 안내 버전을 기록합니다.

### A03 · 높음 · 앱 가입과 서버 가입의 동의 문구·구조가 다름

- 구분: 브라우저 실행 + 코드 확인
- 앱 가입: “의료 진단이 아닌 웰니스 셀프 체크임을 이해했습니다”와 “개인정보처리방침과 이용약관에 동의합니다” 두 개를 요구합니다.
- 서버 가입: 개인정보처리방침과 이용약관을 각각 요구하지만 의료·웰니스 확인은 없습니다.
- 진단 시작: 의료 한계 확인과 개인정보·약관 동의를 다시 요구합니다.
- 실제: 같은 계정 생성 행위인데 채널별 필수 동의 항목과 묶음 방식이 다르고, 서버에는 어느 방식도 저장되지 않습니다.
- 개선: 가입 동의, 서비스 안전 확인, 광고 동의를 목적별로 분리하고 앱·서버가 같은 ID와 같은 문구를 사용하도록 공통 정의를 둡니다.

### A04 · 높음 · 인증 설정과 실제 비밀번호 정책이 충돌

- 구분: 가입 API 실행
- 실제: `/api/public/auth/config`는 `minPasswordLength: 1`을 반환하고 앱·서버 주석도 1자를 허용한다고 설명합니다. 실제 가입 검증에서는 Supabase가 8자 미만을 거절했습니다.
- 결과: 가입 검증 33개 중 30개 통과, 1자 비밀번호 가입과 그 후속 로그인·이름 없는 가입 시나리오 3개 실패.
- 사용자 영향: 화면에서 허용된 입력이 제출 후에야 실패하고, 어떤 길이가 필요한지 사전에 알 수 없습니다.
- 개선: Supabase 실제 정책을 단일 기준으로 읽거나 서버 설정을 최소 8자로 맞추고 앱에 최소 길이와 조건을 제출 전 표시합니다.

### A05 · 높음 · 이메일과 휴대폰 소유 확인이 꺼져 있음

- 구분: 실행 설정 확인 + 코드 확인
- 실제: 서버는 `emailVerificationRequired=false`, `phoneVerificationRequired=false`, `phoneMode=alias`를 반환합니다. 앱과 서버 웹도 “확인 절차 없이 바로 가입”이라고 안내합니다.
- 영향: 타인의 이메일을 먼저 등록할 수 있고, 휴대폰 번호는 SMS 소유 확인 없이 별칭 이메일 계정으로 만들어집니다. 휴대폰 가입자는 비밀번호 재설정도 지원되지 않습니다.
- 개선: 이메일 확인을 켜고, 휴대폰 로그인은 SMS 공급자 연결 후 native 방식으로 전환합니다. 전환 전에는 휴대폰을 로그인 수단으로 홍보하지 않거나 위험을 명확히 제한합니다.

### A06 · 높음 · 통증·어지럼으로 동작을 중단한 사실을 기록할 수 없음

- 구분: 브라우저 실행 + 코드 확인
- 재현: 설문 A10(의자 10회) 진입
- 실제: 안내에는 “통증·어지럼이 생기면 즉시 중단”, 해설에는 “점수 대신 중단 태그를 기록”이라고 되어 있지만 화면 선택지는 ①·②·③뿐입니다. 진행 저장도 이 세 값만 허용합니다. 계산기는 `stopped_question_codes`를 지원하지만 UI에서 만들 수 없습니다. C2, C5, C7, D7 등 중단 안내 문항도 같은 구조입니다.
- 영향: 사용자는 안전을 위해 중단하고도 부정확한 답을 골라야 다음으로 갈 수 있습니다. 결과 정확도와 안전 메시지가 충돌합니다.
- 개선: 해당 문항에 “통증·어지럼·저림 때문에 중단” 선택을 제공하고, 점수 제외와 안전 안내를 함께 저장합니다.

### A07 · 높음 · 회원이 앱에서 계정을 삭제할 수 없음

- 구분: 전체 코드 검색
- 실제: 내 상태에는 프로필, 비밀번호, 주문, 멤버십, 측정 기록, 로그아웃이 있지만 회원 탈퇴·계정 삭제가 없습니다. 서버에도 회원 본인용 삭제 API가 없고 관리자 삭제만 있습니다.
- 영향: 개인정보처리방침이 언급하는 삭제 권리를 사용자가 앱에서 실행할 방법이 없습니다.
- 개선: 본인 재인증, 활성 구독·미배송 주문 안내, 보관 의무 데이터 분리, 삭제/익명화 완료 안내가 포함된 탈퇴 플로우를 추가합니다.

## 4. 마이페이지·결제·광고 문제

### M01 · 높음 · 마이페이지 조회 실패가 빈 데이터로 보임

- 주문 조회 오류는 `[]`, 측정 기록 오류는 `[]`, 구독 조회 오류는 `null`, 프로필 조회 오류는 `null`로 변환됩니다.
- 화면은 각각 “주문 내역 없음”, “측정 없음”, “무료”, “정보 미입력”으로 표시합니다.
- 유료 회원에서 구독 조회만 실패하면 `isPaid=true`여도 멤버십 상세 대신 무료 혜택과 “멤버십 보기”가 노출될 수 있습니다.
- 개선: `loading / success-empty / error`를 분리하고 기존 데이터를 유지한 채 재시도 버튼과 장애 안내를 표시합니다.

### M02 · 보통 · 프로필 저장이 부분 성공할 수 있음

- 저장 순서는 인증 이메일 변경 → 인증 비밀번호 변경 → 프로필 DB 저장입니다.
- 마지막 프로필 저장이 실패하면 이메일 또는 비밀번호만 이미 변경됐지만 화면에는 “저장하지 못했습니다”만 표시됩니다.
- 개선: 변경 항목을 분리 저장하거나 단계별 성공 상태를 사용자에게 보여주고, 실패 후 현재 인증 상태를 다시 읽어 화면과 맞춥니다.

### M03 · 높음 · 광고 고지와 실제 SDK가 다름

- 실제 네이티브 앱은 `@capacitor-community/admob`의 AdMob 배너와 보상형 광고를 사용합니다.
- 개인정보 문서는 Google AdSense와 브라우저 쿠키 중심으로만 설명합니다. 모바일 광고 식별자, AdMob, 보상형 광고, SSV, 기기 권한·동의 정책이 구체적으로 정리되지 않았습니다.
- 현재 실 광고 단위 3개는 비어 있어 Android 빌드에서는 Google 테스트 광고 단위를 사용합니다.
- 개선: 웹 자사 프로모션, 웹 광고, 네이티브 AdMob을 구분해 실제 처리 항목과 제3자·국외 이전을 문서에 반영합니다. 네이티브 동의 관리 요구도 출시 대상 국가 기준으로 검토합니다.

### M04 · 높음 · 유료 서비스 약관이 실제 결제 화면을 뒷받침하지 못함

- 앱은 월 자동결제, 5,900원, 기간 종료 해지 예약을 표시합니다.
- 이용약관은 환불·해지 조건을 “실제 정책으로 작성하세요”라고만 둡니다. 서버 약관은 유료 서비스 절 자체가 없습니다.
- 앱 체크아웃도 “언제든 해지”는 안내하지만 청약철회·환불 조건, 결제 주체, 갱신 시점, 스토어 정책 링크가 없습니다.
- 개선: 앱과 서버에 같은 유료 정책을 노출하고 체크아웃에서 결제 전 핵심 조건을 요약·링크합니다.

### M05 · 보통 · 마이페이지 텍스트와 타입 검사 오류

- “내 정보 수정 및 비밀 번호 변경”은 “비밀번호”로 통일해야 합니다.
- 가입 입력은 한 화면에서 “핸드폰”, 다른 화면과 오류에서는 “휴대폰”을 사용합니다.
- `StatusSections.tsx:224,235`의 union 결과에서 `message` 접근 타입 오류 2건 때문에 `npm run typecheck`가 실패합니다. 프로덕션 빌드는 통과하지만 CI에서 타입 검사를 사용하면 배포를 막습니다.

## 9. 권장 적용 순서

1. 개인정보처리방침·이용약관을 실제 서비스 기준으로 확정하고 앱·서버의 단일 원문과 버전을 만듭니다.
2. 서버 동의 이력 저장과 가입 API 검증을 추가한 뒤 앱·서버 가입 UI를 같은 동의 ID로 연결합니다.
3. 비밀번호 최소 길이와 이메일·SMS 확인 정책을 실제 인증 공급자 설정과 일치시킵니다.
4. 안전 중단 선택지를 설문과 저장·채점에 연결합니다.
5. 회원 탈퇴와 개인정보 권리 행사 경로를 만듭니다.
6. 마이페이지의 오류/빈 상태를 분리하고 프로필 부분 저장을 개선합니다.
7. AdMob·결제 정책을 법적 문서와 체크아웃에 반영합니다.
8. 타입 오류를 고치고 서버 인증·동의·구독·취소에 자동 테스트를 추가합니다.
